# Ahjo Swarm

Ahjo Swarm runs a node in each machine environment. `ahjo help` lists the running node's nouns, each with its verbs; `ahjo <noun>` says what each verb does and `ahjo <noun> <verb> --help` gives its arguments (`ahjo help --all`: every command at once). Commands depend on the areas enabled on that node. `ahjo version` says whether the local node answers (exit 3 when none does); where `ahjo install` put it in place it runs as the systemd user unit `ahjo`. The same commands are MCP tools, one server per area so a client pays only for what it uses: over HTTP `/mcp/<area>` on the node (several as `/mcp/issue,files`; the node's own `config` and `view` are `/mcp/node`, and `/mcp` is every one), and over stdio `ahjo mcp --area <area>` (again for more; none for every one). `/mcp/chatgpt` is a tool set for ChatGPT: the handoff, issue and host tools, plus `swarm_search` to find any other command and `swarm_read`/`swarm_run` to run it as the read or write it is. The areas are `terminals` (session, project, handoff), `harness` (harness, agent), `files`, `issue`, `brain`, `host` (host, service), `scheduled` and `missions` (mission, layout, run).

Commands use `ahjo <noun> <verb>`. Required arguments can be positional or named flags, as can a command's one optional argument (`ahjo file list <path>`); object arguments are JSON. A flag that takes a value takes the next word as it is (`--text --help` is the text `--help`). A word no flag looks like is a value, so a page starting `---` needs nothing special (`ahjo brain write <path> "$(cat page.md)"`); after `--` every word is a value, for text such as `--verbose`. Add `--node <id>` to act on a node through the local node, or `--node <url>` to contact a node directly. Without it, commands address the local node.

Plain output is compact: it leaves out empty fields and says `none` for an empty list. `session read` gives the visible screen by default. Use `--lines N` for the newest N lines including scrollback, or `--all` for all of it. The answer says when it cut. `session search` names each matching session and `session list` shows its harness and state. Before choosing reasoning effort for an agent or seat, read `effort_policy` and the supported efforts from `ahjo agent list --json` (MCP `agent_list`, or ChatGPT `swarm_read` with `command: "agent_list"`). Use `agent show <id>` for an agent and the missions that reference it. `host show` and `mission show` give a summary, with `--full` for every field. Add `--json` when a program parses the answer: stdout is then the answer as JSON, and a failure is `{"error":{"code","message"}}` on stderr. The exit code is 0 when the command was done, 1 when it ran and failed (match on the error's `code`), 2 when the command line was wrong, and 3 when no node answers. An error names the command to run next.

Nouns: `session` (terminal sessions), `file`, `issue` (Beads and GitHub: `issue list` gives each issue's summary, and `issue show` gives its text and family), `brain`, `host` and `service`, `scheduled` (prompts sent into sessions), `agent` and `harness` (agent tools, skills and instruction files), `mission`, `layout` and `run` (mission graphs and their runs; read [missions](references/missions.md)), `view` (the open app; the brain has no page there, it is read in the Ahjo Brain app) and `config`. Before a file `write`, read the file and pass its version as the base, so a stale edit is refused. `harness show-shape --dir D` shows what an agent started in D gets (instructions in load order, skills, hooks, settings, servers, each with its file); use `create-hook`, `edit-hook`, `delete-hook`, `switch-hook` and `edit-setting` to change the files it lists.

Use `ahjo file search-paths <query> --under <folder>` to search one folder and its descendants. `ahjo file stat <path> [<path> ...] --json` gives modification times in input order. To show a screenshot or render to an assistant, `ahjo file list-images <folder>` lists the PNG, JPEG and WebP images under a folder newest first, and `ahjo file read-image <folder> <path>` gives one (up to 5 MiB and 8000 px a side): over MCP as image content, with `--json` as base64. For bytes, use `ahjo file read <path> --base64` and `ahjo file write <path> <encoded-bytes> --base64`. Add `--replace` to overwrite a file with base64 bytes.

The Swarm app’s own settings are in `app.json` on the app’s device: `AHJO_SWARM_CONFIG` overrides its path; otherwise it is `$XDG_CONFIG_HOME/ahjo/app.json` (default `~/.config/ahjo/app.json`) or `%APPDATA%\Ahjo\app.json` on Windows. Read and preserve the rest of the JSON when editing it; the running app reloads changes. `ahjo config show` reads the separate node configuration.

## Sessions and scheduled prompts

Read a session before sending into it; the operator may be working there. `session send` pastes text and normally presses Enter; `--no-enter` leaves it unsubmitted. A receipt says tmux took the input, not that the agent consumed it or finished. If delivery is uncertain, inspect the pane before retrying. Kill only sessions you launched.

To hand work to a coding agent, `ahjo handoff launch <project> <brief>` opens a session in the project's folder (a fragment of its name will do; `ahjo project search <query>` lists the matches) with the launcher's first agent harness and notices on, sends the brief once the agent is ready, and answers when it is working, at most a minute later. Write the brief to stand on its own. It does not answer a question the agent asks first (trusting the folder, signing in): it says so, and the brief goes with `handoff reply` once that is answered. `ahjo handoff show <session> --wait 60` says whether the agent is working, needs input (with the question), finished or idle, with the bottom of its screen, and waits while it works, at most 90 s. `ahjo handoff reply <session> <text>` submits text, or presses an option's number while a menu asks.

The app's Send to Session composes a reference, note and attached file paths into a message; attachments are copied to the target node first. `session send` sends the supplied text only, so prepare any reference and paths yourself. The app leaves a message unsubmitted when it launches a new session.

For recurring work, inspect `scheduled list` and update a matching task instead of duplicating it. Target existing session names (or `user/name`), inspect the receiving session and its input, and write a durable prompt with the purpose, context and expected result. `scheduled create` takes a name, prompt, sessions and either `--every` minutes or a five-field `--cron`; specify an IANA `--timezone`. Use command help for exact syntax. A task sends only to the sessions it was made for, through renames and across a tmux restart (a reboot), where it follows their names: when another session takes one's name on the same server, the task is held (`held` in `scheduled list`; `scheduled show` names such targets in `replaced` before a run finds them) until `scheduled edit <task> --sessions <name>` aims it again. Read back the task and its next run after changing it. `scheduled run` sends immediately; use it only when that is appropriate. The scheduler does not launch an agent. Check the receiving conversation and artifacts to verify consumption and completion.

When asked to build or finish a mission the operator sketched, start with `ahjo mission show <mission>`: one answer with his notes beside what each is on, the steps in run order and what still stops it running. Author whole missions with `ahjo mission export` and `ahjo mission apply`. Use `ahjo mission list-repositories` to find the configured names for `mission run --repository`. For the document fields, notes, staffing, or driving and recovering a run, read [missions](references/missions.md).

For the complete command inventory, see [commands](references/commands.md).
