# Missions

A mission is a reusable graph. An Input card starts it, formations are steps with staffed slots and ports, gates route verdicts, and End nodes end paths as `done` or `rejected`. A run snapshots the graph and staffing at admission; later edits affect later runs. Each step's agents work in ordinary tmux sessions with the harness's access, named `<prefix>-<agent>` so the session list groups a mission's sessions under its prefix.

## Connect

Use the node that owns the mission, as described in [the Ahjo Swarm skill](../SKILL.md). `ahjo help`, `ahjo <noun>` and `ahjo <noun> <verb> --help` are the current command reference; use `--json` for IDs and `--node` on each command when targeting another node. The examples below use the local node. An area can be disabled or a node can run an older build: check its help before relying on a command.

## Pick up a mission

The operator sketches a mission roughly and writes notes on it: on the mission as a whole (what they are trying to build), on steps, gates, limits, the Input card, Ends and wires. Notes are their intent; your job is usually to turn the sketch into a mission that runs. `ahjo mission inspect <mission>` is the whole hand-over in one answer: the intent notes under `about`, the steps in the order a run meets them (numbered as the app numbers them, with who does each, the brief, where it leads, gates with what they check and where pass and fail go), limits with what they cap, every note beside what it is on with its id, author and whether it is resolved, and the `problems` that still stop a run. `--full --json` is the whole definition with every port and slot id, for wiring.

Answer the notes where they are, so the operator sees on the board what you did: `ahjo mission reply <mission> <note-id> --text '<answer or question>' --author <your-name>` asks or answers in the note's thread, and `ahjo mission resolve <mission> <note-id> --text '<what you did about it>' --author <your-name>` closes it with what you did; a later note from anyone opens it again. Leave your own explanations with `ahjo mission note <mission> --target <id-or-title> --text '...' --author <your-name>` (no `--target`: the mission itself; a wire is `From->To`, or `Gate:fail->Step`). `--author claude-7` writes as `agent:claude-7`; give your session's name. `--edit <note-id>` and `--delete <note-id>` change only your own notes; reply rather than rewrite someone else's. Pass `--updated-by agent:<your-name>` to the commands that change the graph, so the app says who changed it last. Notes express intent; briefs instruct seats: translate notes into briefs, staffing and wiring. `ahjo mission notes <mission>` lists the threads as they are stored.

## Author

Read `ahjo mission inspect <mission>` and `ahjo role list` before changing an existing graph, and preserve the draft and notes. Take IDs and port IDs from the returned JSON (`inspect --full --json` or an edit's answer), not guesses. Selectors can also be unique titles; endpoints are `node:port`.

`ahjo mission examples` lists whole missions to start from (best of three with a judge, write and review, plan build check); `ahjo mission new <slug> --example <name>` copies one, staffed and wired, under a new id. Otherwise create an empty mission with `ahjo mission new <slug> --title '<title>'`, then its Input card with `ahjo mission create <slug> --goal '<goal>'`. Add a step with `ahjo formation create <slug> --type solo --title '<title>' --json`; its returned `formation` has `id`, `inputs`, `outputs`, and `slots`. Staff it explicitly with `ahjo formation assign <slug> <step-id> --harness claude --model haiku --effort low` (name the seat with `--slot <slot-id>` when the step has several); choose harness, model and effort for the work. A model the harness does not offer on this node is refused, and the refusal lists the ones it does. Edits answer with what changed, under `changed`, `removed` and the created item. `ahjo role characters` lists saved staffing, and `--role` adds reusable role text. Put task-specific instructions in `ahjo formation set-brief <slug> <step-id> --goal '<instructions>'`, not in a role.

Connect the Input card with `ahjo mission wire <slug> --to '<step-id>'`. Connect later ports with `ahjo formation wire <slug> '<from-id>' '<to-id>'`; a bare id takes a step's only port, an Input's `out` and an End's or gate's `in`, and a gate leaving needs `:pass` or `:fail`. Name the port as `id:port` when there are several. Output ports can fan out; a step waits for all inputs. `--join` adds an input to an occupied step input. Route every step output and both gate verdicts to a step, gate or End. Add Ends with `ahjo end create <slug> --outcome done` or `--outcome rejected` and wire to `<end-id>:in`. `ahjo mission validate <slug> --json` must have no errors before admission; resolve warnings about unintended unreachable nodes too. Edit nodes in place to preserve edges. `ahjo mission edit` accepts one JSON authoring operation when needed; prefer named commands and their help.

`ahjo layout show <slug>` reads positions; `ahjo layout edit <slug> '{"arrange":true}'` replaces them with arranged positions. Arrange deliberately after substantial rewiring, and read the layout back; it changes the operator's canvas.

## Agents and sessions

A slot names the agent who works it; without a name it is the step's title in words. A run starts that agent's session when it is not live and leaves it running; the next run uses it, as it is and where it runs. Only a session a run started counts: one that merely has the agent's name, such as one a person started, is never typed into, and the step works in a session of its own beside it (`<prefix>-<agent>-<tag>`), ended with the attempt. A second attempt that wants the agent's session while it is busy gets its own the same way. `ahjo formation agent <slug> <step-id> --agent <name>` names it (`--slot` on a team). `ahjo formation fresh <slug> <step-id> on` makes every attempt start in fresh sessions, `<prefix>-<agent>-<run>-<attempt>`, ended with the attempt: a best-of-n step is a fresh step with a judge gate whose fail loops back to it and a Limit card of n rounds with `--when-spent best`. The prefix is the slug's letters and digits; `ahjo mission prefix <slug> --prefix <letters-and-digits>` sets another. Do not type into a mission's session while its step runs.

## Inputs and outputs

`ahjo mission input <slug> --name <name> --kind text --required --description '<meaning>'` declares an input (`text`, `file`, or `folder`); `--optional` and `--delete` change or remove it. With no declarations the run takes a required `brief`. Reference inputs in step briefs as `{name}`; `{{name}}` is literal. File and folder inputs are existing absolute paths on the node. `ahjo formation add-output` or `formation set-port` sets a step port's `text`, `file`, or `folder` kind. File and folder outputs are copied into the attempt's evidence and the copy's path is routed. Declare a promised mission output using `ahjo mission output <slug> --name <name> --kind file --from '<step-id>:<port-id>' --required`; a missing required output on a done path fails the run. Check exact flags with command help.

## Gates

`ahjo gate create <slug> --title '<title>' --criterion '<criterion>' --kinds formation,human --json` creates a judge followed by human sign-off. Create a separate solo judge formation and attach it with `ahjo gate judge <slug> <gate-id> --chain <judge-id>`. Wire work output to `<gate-id>:in`, and `<gate-id>:pass` and `<gate-id>:fail` to their next destinations. A fail may loop back to work; cap loops with a Limit card. A human-only gate is the default. A code gate checks `output_contains` or `output_absent` version 1; it does not run shell commands. Kinds execute in code, formation, human order, stopping at failure.

The runtime supplies each seat its output contract; a judge also returns a fenced verdict block containing `verdict` (`pass` or `fail`), `reason`, and `evidence`. Do not direct a seat by typing into its session. Inspect run evidence and the seat if a result fails to route.

## Limits

Runs have no automatic limits. `ahjo limit create <slug> --target <step-id> --rounds 3` caps step attempts; `--target input` covers the whole mission. `--time 30m`, `--warn 5m` and `--tokens <count>` are optional. The default on exhaustion is to block; `--when-spent fail` ends the run, while `--when-spent best` selects among judged attempts at a suitable send-back gate. Use `limit update` and `limit delete` to change cards. A human pick or a grant needs the operator's authority.

## Run and watch

Start only with the authority and inputs appropriate to the work. `ahjo mission run <slug> --inputs '{"brief":"<work>"}' --actor 'agent:<session>' --json` returns `runId`; use named values in the JSON object for declared inputs. `--cwd` selects an existing workspace; `--work` identifies the owning work item and repeated `--context-paths` supply references. `ahjo formation run` starts at one step. If the receipt is lost, inspect `ahjo run list --mission <slug>` before starting another.

Drive with `ahjo run wait <run-id> --json`. The default `needs-you` returns when a gate needs a decision, the run blocks, or it ends. The result has `outcome`, `status`, `cursor`, `asks`, and exact answer commands in `next`; exit 0 means the wait answered, not that the run succeeded. After an answer, wait again using `--since <cursor>`. `--until final` waits for the end, `--until any-change` reports the next change, and `--timeout <seconds>` bounds a wait. On timeout, wait again with the returned cursor. Inspect `ahjo run status`, `run seats`, `run logs`, `run attempts`, and `run evidence` for state, attempts, problems, briefs, produced file paths and (`written`) the files agents wrote in the run's folder. Use `--step` with evidence or attempts to narrow the result. Read final status and outputs before reporting success; a picked result carries failed work selected for continuation, so inspect its findings before using it.

## Decide

For a human gate, use `ahjo run gates <run-id> --json` and `ahjo gate request <run-id> <gate-id> --json` to inspect its criterion, inputs, consequences and current request. Decide only with the operator's authority. Use the exact `ahjo gate approve` or `ahjo gate reject` command from `run wait`, including the current `--requested-seq`; `--response` travels onward on approval or becomes rejection feedback. For a best-attempt request, inspect candidates and `run attempts`, then use the offered `gate pick` with its attempt and current sequence. On a stale request, read it again rather than reusing the sequence. Wait again after the decision.

## Recover

Read `run status` and `run evidence` for the block and whether resume is allowed. A seat that went quiet without saying it was done is reminded twice, then its step blocks with `seat_idle_without_sentinel` (or `seat_stuck` when it never took its brief, with what its screen said); even `run wait --until final` returns then. Its terminal is kept: resuming asks that seat once to go on, and a closed terminal blocks again with `seat_gone`, which needs `--mode redispatch`. Resolve the named cause, then `ahjo run resume <run-id> --reason '<reason>'`; use `--mode redispatch` when a lost seat must run again. A spent limit may require an authorized `--grant` or `--pick-best`; otherwise `ahjo run abort <run-id> --reason '<reason>'` stops that run. Preserve its briefs and artifacts while investigating. In a repository run, what a step that failed or was stopped wrote is kept on the branch `ahjo/run-<run-id>-kept/<step-id>-<attempt>`, named in the block reason and in a `workspace_kept` event of `run status`; `run delete` removes it. A final failed or canceled run needs a new run after fixing its cause. Follow a resumed run with `run wait` again.

`ahjo run delete <run-id>` removes a finished run with its record, artifacts and the folder Ahjo made for it; a repository run must be landed first. `ahjo mission delete <slug>` removes a mission. Delete only with the operator's say-so.
